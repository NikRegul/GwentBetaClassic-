# Проверка предложений другого агента по исходникам

Проверен присланный текст и текущие `duelSession.ws`, `duelPublicResponseAI.ws`, `duelAIPass.ws`, `duelClone.ws`, `developmentBoardMenu.ws`. Главный диагноз справедлив: выбор строится из ограниченных симуляций, моделей ответов и многих эвристик. Однако это список гипотез, а не доказательство дефектов каждого перечисленного места или гарантированного роста силы.

| Утверждение или предложение | Оценка по коду |
|---|---|
| Поиск преимущественно неглубокий | Верно. Есть точный ход, продолжение, ограниченные ответы противника, догон и отдельный DFS оставшейся руки. Единого глубокого поиска всех допустимых действий нет. Формулировка «только 1 ply» упрощает устройство. |
| Нужен единый учёт возможных ответов соперника | Полезное направление. Оценки паса, снятия и ответов должны использовать совместимые знания. Но уже существующая модель шире трёх опасных карт. |
| Модель ответов статическая и не использует reveal/play | Неверно. `CBetaGwentPublicResponseAI.Initialize` собирает публично сыгранные оригиналы, раскрытую руку, вычитает увиденные копии из исходного списка на максимуме и использует веса совместимых профилей на других сложностях. Это эвристическая модель, а не полноценное распределение вероятностей текущих рук. |
| `publicBurst` — константа | Нет: начальное значение 10 далее меняется по раскрытой руке и пулу возможных карт. Это грубая верхняя оценка, её действительно можно улучшить. |
| Выборок разных seed сейчас нет | Уже есть `AiSpyForecastDeck(sample)`: канонический порядок собственной колоды, отдельные seed по номеру выборки и последующее перемешивание копии. Критиковать малое число выборок можно; представлять сам подход отсутствующим — нельзя. |
| Любая погодная линия требует разных seed | Не вся погода случайна. Нужно различать неопределённый выбор цели, неизвестный будущий ход и детерминированный урон. Дополнительные выборки нужны там, где они меняют оценку риска, и стоят дополнительных симуляций. |
| `Score` и `CountLocation` пересчитывают `SBetaGwentMatchSnapshot` | Неверно: они линейно обходят `live` и читают снимки карт. Индекс зон может ускорить эти обходы, но ускорение всего ИИ в 10–100 раз из этого не следует. Нужен нативный профиль затрат. |
| Клонирование и повторная инициализация RNG стоят времени | Верно: создаётся графовая копия с `CBetaGwentCloner`, затем отдельный генератор симуляции переинициализируется. Объектный пул или оптимизация копирования возможны после измерения. Полный Reset должен сохранять изоляцию очередей, запросов, ссылок и клонов. |
| Можно просто заменить RNG на xorshift | Генератор реального матча нельзя менять как локальную оптимизацию поиска. Отдельный генератор только для предположений — иной проект, требующий проверки распределений, воспроизводимости и отсутствия влияния на живую игру. |
| `knownHand >= CountLocation(1,8)` — ошибка границы | Обоснование неверно. Подходящая раскрытая карта возвращает true внутри предыдущего цикла. `knownHand` считает подмножество той же руки, которую считает `CountLocation`; кража не делает его больше общего размера. Замена >= на == не исправляет показанного бага. |
| При сбое симуляции паса безопаснее вернуть обычный положительный счёт | Опасный совет. Положительный счёт не учитывает последующее срабатывание засады, таймера или возврата карты. Текущий пессимистичный ответ может стоить лишней карты, но оптимистичный возврат способен разрешить проигрышный пас. Лучше явно отмечать неизвестный результат и чинить причину отказа. |
| `effect + specialMode` полностью заменяют ID | Для части карт да, но у Игни, Ширру и многих других составных способностей общий `effect=34`, а `specialMode` не описывает всю семантику. Нужны дополнительные признаки возможностей карты или общий анализ её графа, а не механическая замена ID. |
| Восстановление `aiSimDamp` после 30 секунд ожидания | Ожидание игрока само по себе не ускоряет исполнение скрипта. Текущий замер включает сумму синхронных шагов и их пик, а не паузу игрока. Сглаживание всплесков полезно проверить; безусловный сброс каждый раунд может вернуть лаги. |
| MCTS/alpha-beta гарантированно дадут +15–25% | Необоснованное численное обещание. Без реализации и независимых испытаний такой процент неизвестен. |

## Что потребуется для настоящего дерева

Одного `AiSimClone()` недостаточно. Нужен генератор допустимых действий: карта, ряд и позиция, вариант создаваемой карты, цель, последовательность нескольких выборов, лидер и пас. Нынешний `AiSimPlay` сам выбирает ряд и цели существующими эвристиками; превращение этой функции в цикл не даёт полного перебора стратегий.

Следует учитывать скрытую информацию, случайные исходы, ходы одной стороны подряд после паса, переходы раундов, короны, остаток руки и будущую ценность карт. Оценка листа только по текущим очкам способна усилить уже наблюдаемую ошибку чрезмерного вложения в первый раунд. Нельзя механически менять знак оценки на каждом ребре negamax, когда действующий игрок не сменился.

Для поиска с неполной информацией существуют специальные варианты, например Information Set MCTS. Это основание рассмотреть такой прототип, а не обещание его преимущества в данном движке. Первичный источник: [Cowling, Powley, Whitehouse, Information Set Monte Carlo Tree Search, 2012](https://eprints.whiterose.ac.uk/id/eprint/75048/1/CowlingPowleyWhitehouse2012.pdf).

Бюджет времени полезен вместе с ограничениями узлов и выполнением по частям. Монолитные 100 мс на главном потоке уже являются заметной задержкой кадра. При равном seed лимит по числу операций даёт воспроизводимые решения; один лишь wall-clock может менять выбор из-за фоновой нагрузки.

## Предлагаемый порядок

1. Сохранять конкретные ошибки из партий и проверять полные альтернативные продолжения. Уже подтверждены пропуск полезного дешёвого розыгрыша и чрезмерный резерв одинаковых бронзовых ответов после сухого паса.
2. Измерить затраты в настоящем WitcherScript: клонирование, счётчики зон, запросы целей и отдельные этапы поиска. Индексы и повторное использование объектов вводить с проверкой всех изменений состояния.
3. Объединить знания о возможных ответах: исходный список, публичные копии, раскрытия, создание и повторный розыгрыш карт. Не использовать закрытые личности заменённых карт человека.
4. Прототипировать более глубокий поиск в узких концовках с полноценным набором действий и ограничением времени на один шаг. Сравнивать с текущим ИИ на общих раздачах и независимом расписании.
5. После этого расширять выборки случайных линий и настраивать веса на разнообразных фиксированных противниках. Тюнинг только против своей предыдущей версии не доказывает улучшения игры против человека.

Это направление дальнейшей работы. В 0.9.1f не заявляется внедрение MCTS, обученной модели или гарантированного общего роста процента побед.

## Второй текст: обещания уровня сильного человека

Второе предложение правильно выделяет клонируемый симулятор, учёт скрытых карт, разнообразных противников при настройке и более точную игру в концовках. Но по этим свойствам нельзя установить человеческий уровень, предел силы, сроки реализации или прирост побед. Приведённые Tier 0–2.5 не определены измеримым испытанием.

| Утверждение | Проверка |
|---|---|
| Скрытая рука не позволяет честному ИИ превзойти сильных людей | Неверно как общий предел: люди тоже не видят скрытую руку. Pluribus превосходил профессионалов в покере с неполной информацией. Это контрпример общему запрету, а не доказательство достижимости такого результата нашим Gwent-ботом. |
| Потолок точности 70–80%, максимум побед 65%, неизбежные поражения 10–15% | Эти числа не выведены из правил, исходников или результатов испытаний. Не определены соперники, распределение колод и даже метрика «идеальной точности». По ним нельзя планировать работу. |
| AngelScript ограничивает нас 200–400 симуляциями | Игровая логика написана на WitcherScript; интерфейс — на ActionScript 3. Клонирование действительно может быть дорогим, но указанный лимит не измерен. Нужен профиль настоящего исполнения с затратами по этапам и пиком времени одного шага. |
| MCTS заведомо слабее alpha-beta глубины 3 | Не установлено. Оба подхода требуют корректной работы с неизвестной рукой, случайными исходами и доступными действиями. Выбор следует делать по прототипам и измерению качества при одинаковом бюджете. |
| Разных выборок RNG вообще нет | Для добора шпионов они уже есть в `AiSpyForecastDeck(sample)`. Расширение на другие действительно случайные эффекты — полезная гипотеза. Детерминированная погода не становится случайной из-за смены seed. Общие случайные числа для сравнения кандидатов сами по себе не являются ошибкой. |
| Для каждого preset достаточно фиксированного лучшего обмена и первого хода | В пуле 46 колод. Обмен зависит от фактической руки, а первый ход ещё и от стороны, соперника и поля. Условная дебютная политика может помочь; единственная фиксированная последовательность не решает задачу и повышает предсказуемость. |
| При шести картах концовка содержит не более 720 вариантов | 6! считает только перестановки шести объектов. В дереве есть пас, выбор рядов, целей, режимов и новые карты от способностей. Скрытую руку нельзя подставлять как известную. Даже без лидеров и погоды полный набор действий этим числом не ограничен. |
| Endgame solver за два дня гарантирует отсутствие проигранных выигрышных концовок | Гарантия возможна только внутри точно определённого класса позиций при полном переборе допустимых продолжений и корректной информации. Для общего случая в тексте ни такого класса, ни доказательства нет. При неизвестной руке выигрыш при подсмотренной раздаче не равен стратегии, гарантирующей победу. |
| Beam search можно сделать за 30 строк | Ограниченное расширение нескольких последовательностей полезно проверить. Но оценка будущей руки, разрешение всех запросов способности, бюджеты, кооперативное выполнение и сохранение состояния не исчезают от короткого цикла. Число строк не оценивает объём надёжной реализации. |
| Без человеческих реплеев self-play не может дать сильную стратегию | Слишком категорично: Pluribus обучал базовую стратегию самоигрой без данных человеческих или прежних ИИ-партий. Разнообразные фиксированные соперники и независимая проверка всё равно полезны для нашего стенда; сравнение только с собой не измеряет силу против человека. |
| Сильный ИИ никогда не пасует, когда ведёт | Неверно для Gwent и противоречит исходному отзыву пользователя. При безопасном отрыве пас сохраняет карты; продолжать нужно, если возможные ответы, таймеры или засады делают пас плохим. |
| Четыре изменения дадут +15–20% и top-human уровень | Не подтверждено. Проценты от разных изменений не складываются автоматически; результат зависит от их взаимодействия и соперников. Точные сроки, «40% исхода за первые ходы», «80% результата» и +2% от ML также не подкреплены данными. |

Первичный источник контрпримера: [Brown, Sandholm, Superhuman AI for multiplayer poker, Science, 2019](https://noambrown.github.io/papers/19-Science-Superhuman.pdf), описание результата и self-play на первых двух страницах. Это не рекомендация переносить покерный алгоритм без адаптации к Gwent.

Из второго текста стоит взять более широкий ограниченный поиск догона, точные небольшие концовки и настройку дебютных решений по фактической руке. Сначала нужны измерения затрат, полный набор допустимых действий для выбранной подзадачи и сохранённые ошибочные позиции. Предел силы и сроки заранее неизвестны.

Практический результат текущей работы скромнее обещаний: в 0.9.1f исправлены два подтверждённых выбора после паса; на независимых 368 партиях против 0.9.1e получены 181 победа, 183 поражения и 4 ничьи. Общего преимущества не подтверждено. Из этого нельзя ни обещать человеческий уровень, ни выводить невозможность дальнейшего усиления.
